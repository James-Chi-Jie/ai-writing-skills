# 故事驱动的知识表达：写作与读解通用框架

> 目的：让读者沿着一条可靠的探索路径形成理解；不是把知识包装成虚构故事。适用于技术博客、论文/文章解读、工程复盘、知识性随笔。非知识性写作、合同和需要逐项核对的材料不强制套用。

## 一句话定义

故事 = **有意义的问题 + 逐步获得的信息 + 可检验的认识改变**。

不是把所有内容变成“主角遇到困难、英雄登场、最终胜利”，也不是为每一段添加悬念、对话或情绪。

写之前先建立一张内部叙事卡（默认不必展示给用户）：

| 字段 | 要回答什么 |
|---|---|
| 读者 | 已经懂什么？暂时不懂什么？ |
| 中心问题 | 读完后应该能独立回答什么？ |
| 起点 | 哪个真实场景、反常识观察或矛盾最适合引出问题？ |
| 读者直觉 | 一个合理的人首先会尝试或相信什么？它是否其实可行？ |
| 关键转折 | 新证据/限制/反例如何改变原来的解释？ |
| 可见机制 | 哪一步输入变成哪一步输出？如何验证？ |
| 终点 | 新认识适用到哪里？还有什么不能推出？ |

## 推荐的故事节拍（可删、可合并、可换序）

1. **情境 / 起因**：给出具体且相关的问题。不杜撰场景为真实历史；示意案例明确为“假设”。
2. **探索 / 原有理解**：让读者有机会先用已有知识推断；公平呈现可行的替代方案。
3. **转折 / 关键差异**：出现真正的约束、反例、数据或实验结果。转折必须由事实支持，不以“旧法必败”强行制造戏剧冲突。
4. **发现 / 解释机制**：沿同一例子展示输入、过程、输出，必要时给公式、代码或真实结果。
5. **验证 / 回响**：重答开篇问题，区分事实、解释、假说，指明限制和接下来的自然问题。

检查“连续性”而不是检查是否写满五节：每一个新概念，都应该回答上一步留下的问题；否则它更像字典条目而不是故事。

## 两种任务入口：创作与读解

### A. 从零创作文章（CREATE）

- 先核对事实和阅读对象，锁定一个主问题；选定能贯穿全文的例子（不一定是拟人化故事）。
- 先设计理解路径，再确定章节标题；每节标注“读者在此之前知道什么、此节新增了什么证据、读者因此能推导什么”。
- 若文章有关键推论，用最小算例/实验或权威来源支持；没有证据时保留不确定性。
- 文中术语、公式、图示和引用为推进理解服务；可为审稿保留更详细的证据/验算记录。
- 创作博客需遵守上级 SKILL.md 的**全文文字确认后才能实际生图**门禁；叙事提纲不等于作者批准图片。
- 对于反思随笔，可用“亲历事件→认知冲突→重新理解→行动”作为故事弧，不杜撰作者经历、感受或对话。

### B. 讲解/解读已有文章、论文或报告（EXPLAIN）

**先理解和核查，再重排叙述，不可先编故事再找事实匹配。**

1. 取得原文/可靠摘要并记录来源、作者、发表时间、适用版本；无法取得全文时标明覆盖范围，不能假称读完全文。
2. 建立“原作者主张—所用方法—实际证据—限制”的核对表。区别研究目标、设想架构、原型实现和已验证效果。
3. 找出读者最可能的认知入口：为什么作者认为这是个问题？此前的办法为什么不足？有哪些看似合理的替代方案？
4. 选一种叙述路径：**问题探索型**（why/how）、**实验追踪型**（假说→方法→结果）、**概念纠偏型**（常见理解→反例→准确解释）、**工程决策型**（需求→约束→取舍→验证）。
5. 按故事顺序讲解，但对事实必须能够反向映射到原文；区分“作者明确说的”“我用于教学的类比”“由事实延伸的工程判断”。
6. 对关键机制展示最小例子；对数据说明指标、对照组、条件和不能推出的结论。
7. 最后用一段明确回答“作者到底证明/提出了什么？没有证明什么？对读者有什么可迁移价值？”

不应：
- 把作者的研究原型说成已广泛部署的产品。
- 把相关性、模拟实验或吞吐优化说成模型能力全面提升。
- 把你设计的类比/例子讲成论文中的原始实验。
- 由于自己知道背景知识而替作者补造动机、过程或历史对话。
- 为了故事节奏忽略核心反例、条件或负结果。

### C. 改写与审稿（REVISE）

- 先标出知识点清单、跳跃的前提、过早抛出的术语以及重复问题。
- 不先做辞藻润色，而是重组认识顺序：已知→疑问→有依据的新发现→验证。
- 技术错误、事实缺失先修正；修辞优化不得覆盖技术准确性。
- 作者指出“为什么不直接用更简单的方法”时，优先检查原叙事是否建立在假的必要性之上。

## 节奏控制

- 引人好奇不等于处处设悬念：每个关键问题要有合理时间内的回答。
- 一节只推进一个主要理解台阶；陌生术语一次引入一个主要概念。
- 优先用一个连续的例子而非每段换新类比；类比在不成立的边界应及时停止。
- 明确展示输入→动作→输出，但不要每节都套“首先/然后/最后”。
- 允许简短的结论先行、表格、清单、公式和代码。用户只要事实摘要/清单时不强迫戏剧化。
- 长文适合完整故事弧；短问答可用**微故事**：场景/疑问一句 → 核心差异两三句 → 准确回答一句。
- “讲故事”是解释策略，不等于必须输出故事体裁或第一人称、必须写人物、冲突、五段式与煽情结尾。

## 事实与证据围栏

- 叙事不覆盖证据：所有重要事实/日期/数字/论文结论能够找到来源或明确标为示例。
- 可明确区分：**原文事实 / 研究或实验限制 / 教学类比 / 助手推论 / 未知**。
- 先验上合理的替代方案必须公允讨论；不要把教学路径误写为真实技术发明史。
- 讲创新点时说明与基线的比较条件；不要把“常见/便于实现”写成“只有这样才能实现”。
- 关于安全、医疗、法律、合同、财务等高风险内容，保持证据与适用范围优先；若叙事会掩盖必要的行动步骤或风险，转用清晰的非故事式结构。

## 例：Token ID 的必要性

错误的强行故事：
> 模型必须大量计算字符串，于是科学家只能把文字变成数字 ID，再进行矩阵乘法。

准确的探索式故事：
> 我们已经有一个 Token 字符串，为什么还要把它转换为 ID？先想一个更直接的方案：用字符串直接查表，也能得到同样的 Embedding 向量。所以 ID 并不是 Transformer 在数学上不可缺少的前提。整数 ID 带来的是真实的工程便利：统一词表索引、批量查表、将输入和训练目标类别映射到同一个离散词表。真正送入后续 Q/K/V 数值运算的是 Embedding，而不是 ID 自身。

这个案例证明：好的叙事允许出现“最简单的办法其实可行”的转折。

## 例：解读 Super-agent 研究

- 起点：使用者同时处理许多会话时，注意力和任务协调成为瓶颈。
- 探索：全部塞进单 Session 与分成独立 Session 各有问题。
- 设计：用 Router 保持协调，用 Worker 运行具体工作；通过 Trigger 路由后续事件。
- 验证：区分任务完成时间、Router 调用/Token 开销与真实编码能力；实验若模拟编码工具，不可据此宣称代码质量变好。
- 回响：讨论可靠长任务的调度与状态管理，指出原型与实际部署差距。

这里的“用户成了项目经理”可以是教学类比；若作者没有使用过这个说法，必须明确它是解释者的比喻。

## 读者测试（无需每次都问用户）

在陌生读者立场判断：
1. 开头有没有清晰、真实的疑问，而不是先扔定义或名词？
2. 读到转折时，能说出哪条事实让理解发生变化吗？
3. 从上一节到下一节，读者知道为什么现在要学这个概念吗？
4. 去掉形容词、拟人化和悬念后，论证仍然成立吗？
5. 读者能否复述核心机制、证据与边界，而不只是记住比喻？
6. 若这是文章解读，能否追溯哪些是作者结论，哪些是讲解者的引申？

- [Blog Post Writer](https://github.com/JayRHa/agent-skills/blob/main/blog-post-writer/SKILL.md)：技术文章的具体钩子、例子和读者可执行结果。
