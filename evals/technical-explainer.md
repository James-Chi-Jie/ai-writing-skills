# Technical Explainer — 教学与写作手工评测集 v0.8

## 测试 1：系列文章衔接
**输入**：我已经写了 CNN，下一篇准备写 RNN，后面是 Transformer。给我一个有联系的大纲。

**期望行为**：以问题驱动，解释共享参数的不同维度和 RNN 的状态传递；不声称 RNN 是 CNN 加上记忆模块；区分教学顺序和严格演进史。

## 测试 2：读者仍不理解
**输入**：RNN 不是和 CNN 一样共享参数吗？为什么每个词的结果不同？

**期望行为**：区别训练参数和动态状态；提供可手算例子，最好通过 h_t = 0.5 x_t + 0.8 h_(t-1) 展示权重固定、状态变化；不能简单重复定义。

## 测试 3：图文内容设计
**输入**：给这篇 RNN 文章做配图计划。

**期望行为**：每张图有明确教学目标；优先出参数共享与状态传递的关键图；检查箭头/时间步/公式；不把大量文字挤进一张复杂图。

## 测试 4：文章语言自然性
**输入**：下面这篇技术文章有明显 AI 味道，请改写。

**期望行为**：改善抽象套话、重复提问与机械过渡；保留真实逻辑、技术准确性和作者表达风格。

## 测试 5：计算如何承载历史信息
**输入**：上一步输出参与下一步我理解，但过去信息到底如何通过计算传到第三步？它是不是黑盒？
**期望行为**：提供可手算的三步递推，例如 x=[1,0,0]，h_t=0.8h_(t-1)+x_t 得到 1、0.8、0.64；展开表达式；指出简化假设以及计算与语义可解释性的区别。

## 测试 6：图片采用语义文件名，不以编辑顺序为身份
**输入**：为技术博客交付七张插图，不要在图上写“图X”，并且之后可能在文章中间新增配图。
**期望行为**：画布、资源文件名和正文引用均不使用编辑编号；文件名按语义命名，如 `token-id-embedding-lookup.png`。中间插图不导致其他图片重命名；保留时间步、层数等具有技术含义的数字。


## 测试 7：作者卡在 BPE 频次统计
**输入**：“相邻片段出现的次数，合并频率，这个如何理解？”
**期望行为**：停止追问下一道题，针对 `low / lower / lowest / low` 逐词列出相邻对及频次；明确重复样本影响计数；展示合并后重新统计。不得仅复述 BPE 定义。

## 测试 8：大词表收益解释不充分
**输入**：“通读下来还是大词表好，没看到缺点。”
**期望行为**：固定隐藏维度和同一文本，选一个两种词表下均为 1 Token 的反例；解释词表相关参数和标准完整输出投影成本、区分单步计算与整体延迟；避免“大词表查表必然慢”的断言。

## 测试 9：词表大小与序列长度混淆
**输入**：“programming 是大词表，pro/gram/ming 是小词表，为什么 programming 会导致词表变大？”
**期望行为**：识别两个数量的混淆，展示小词表已有三个条目、大词表在保留这些条目基础上新增完整单词，从而词表条目 3→4，而该文本 Token 数 3→1；先修复该前提，不能继续堆 logits 公式。

## 测试 10：参与式学习边界
**输入**：“我先不回答，因为前面的实验没有理解。”然后用户理解后说“继续”。
**期望行为**：先修复解释而非强迫答题；理解后直接进入下一测试。真实实验标明工具、语料、版本及实际运行状态；玩具 BPE / SentencePiece 不冒充 GPT/tiktoken 数据。

## 测试 11：Token ID 是否参与 Transformer 的数值计算？

**输入**：“你说 Token 参与大量计算，但我觉得 Token ID 只是 Embedding 的下标。Token ID 真的参与 Attention 的矩阵乘法吗？如果不会，为什么说 ID 是必须的？”

**期望行为**：
- 立即修正混淆：Token 文本不参与 Transformer 浮点向量运算；Token ID 参与**索引**与训练目标类别定位，不直接作为 Q/K/V 矩阵乘法中的连续数值特征；Embedding/隐藏状态参与向量计算。
- 承认 `Dictionary<String, Vector>` 可直接取得同一向量，替换为整数 ID **不是数学必要性**；给出的工程收益仅限紧凑索引、批量查表、词表输入输出位置的统一。
- 说明查到相同 Embedding 后的后续计算可以相同，不能把“需要大量计算”误写为“ID 自身参与大量算术”。
- 必须回到文章相应段落调整问题与论证；不能只在聊天中纠正，却在正文保留原来的错误动机。

**不合格**：声称“必须转换成整数，GPU 才能计算 Token”，或将 Token ID 与 Embedding 一起列作 Attention 的矩阵输入。

## 测试 12：问题驱动不等于硬造旧方案的缺陷

**输入**：“既然可以用字符串直接查 Embedding，那还用 ID 干什么？这是不是多此一举？”

**期望行为**：先承认字符串查表可行，再准确界定整数编号作为工程索引的好处，以及其与训练后向量的职责边界。只有在说明比较条件后才论证代价；如没有数学上的必要性，就明确写明“可选设计”。保留“读者能复述为什么这么做”的教学目标，但不为了完成“旧方案→新方案”模板捏造不可行性。

**不合格**：只定义“ID 是行号”，或说“字符串没有办法进入神经网络，所以必须转换为整数”，而不解释字符串查表后可得到向量。

## 待验证的迁移测试
在一篇新的 Go 服务端或 iOS 并发文章中，遇到作者重复“不理解”反馈时，是否能识别隐藏前提并用固定变量的对照例子重建因果；本次 Tokenization 案例不能单独证明跨主题有效。

## 测试 14：故事转折不得靠虚构数学必要性

**输入**：“写一篇《为什么 Token 一定要用整数 ID 而不能用字符串》的科普文章，要像故事一样有反转。”

**期望行为**：先纠正标题中的“必须”前提；让字符串字典查到同一 Embedding 的反例成为真正转折；说明实际整数 ID 作为稳定词表索引、批量嵌入查表与训练目标定位的工程优点；重写标题和论证，拒绝杜撰 GPU 无法处理字符串的说法。

**不合格**：以“旧方法彻底失败”制造高潮，或让 Token ID 直接参与 Attention 矩阵计算。

## 测试 15：用户只要短答案时使用微故事

**输入**：“不用写长文，三句话说清 Router 和 Worker 为什么要分开。”

**期望行为**：用“协调与执行彼此牵制”作为真实问题，以 2–3 句给出职责与作用；不机械输出五个戏剧章节、不扮演人物对话。

## 测试 16：叙述型文章完整正文仍需作者审批后再生图

**输入**：“把现有 Transformer 正文升级成更有故事感的版本，然后配图。”

**期望行为**：先重组正文的因果线索，交付包含全部章节、例子、公式和结论的完整文字版，等待作者明确确认后才调用生图；图计划可以先用纯文字描述。故事化不绕过原有全文确认门禁。

**不合格**：大纲一确定就批量生成图片，或把“继续”视作全文批准。

## 测试 18：正式材料与个人随笔的模式边界

**输入 A**：“把这个合同付款条款复核一下，给我对比表和风险点。”
**期望 A**：保留逐条核对和金额/支付节点的显式对照，不把核算结果改写成跌宕起伏的故事。

**输入 B**：“我想写篇关于一次职业挫折后重新认识自己的随笔，先帮我找叙事结构。”
**期望 B**：可采用“真实经历→原有认知→新观察→认识改变→行动”的故事弧；不自行编造当事人经历、情绪、对话。

## 测试 19：低阅读成本不是短篇幅

**输入**：“我写文档时，会假设之后给一个没有耐心的自己看。你从这个视角出发，觉得文章应该怎么改？”

**期望行为**：
- 明确区分低阅读成本与短篇幅；不以字数、段落数或删减技术细节作为优化目标。
- 让读者尽早知道文章要解决的问题、重要性和理解目标；对具体实用问题尽早给出答案，对需要推导的原理文章先给清楚的理解路线，不为悬念隐藏答案。
- 尽量使用一个稳定例子，控制变量变化；每段都推进因果链、解释必要概念、验证结论或交代重要边界。
- 删除重复表达、装饰性过渡和无关扩展；保留理解核心机制所必需的推导、计算、证据与限定。
- 通过清晰标题和渐进式信息层次降低扫读与深入阅读成本；不机械增加摘要框、表格或图示。

**不合格**：
- 把文章改成极短摘要，省略关键推理或把多个步骤压缩成术语。
- 只追求“先给结论”，却没有交代结论成立的原因和适用边界。
- 为了显得全面，把相邻主题与大量高级技术一起塞进主线。

## 测试 20：控制文章范围，不把相邻技术全部塞入主线

**输入**：“这篇文章既要讲 KV Cache 为什么能减少重复计算，也想把 GQA、量化、PagedAttention、滑动窗口的原理都讲完，不然会不会不完整？”

**期望行为**：
- 识别本篇唯一主问题，并判断读者理解它所必需的内容。
- 对相邻技术只做足以说明边界或后续方向的简短定位；将深入机制留给真正讨论推理性能、缓存管理或注意力变体的后续内容。
- 说明“完整”是当前问题的因果链和关键限制完整，不是把相关技术目录全部覆盖。
- 保留对当前结论有实质影响的代价和限制，例如 KV Cache 的显存成本与并发影响。

**不合格**：
- 将相关技术全部列成一串名词，导致主问题失焦。
- 为了缩短文章而删除 KV Cache 成立的关键原理，或为了覆盖面把文章扩展成推理系统综述。
